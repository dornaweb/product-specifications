# ADR: Store Product Specification Values as a Versioned Value Map

## Status

Approved

## Context

A product carries the values for the specifications its assigned Specification Set
composes. v1 stores those values as a denormalized snapshot across two product meta
keys, written by `ProductSpecifications\ProductSpecificationsMetabox::action()`:

```txt
_dwps_table                  the assigned specs-table post id
_dwps_specification_table    an ordered array of group snapshots
```

The snapshot copies every label into the product:

```php
[
    [
        'group_id'   => '12',
        'group_name' => 'Display',
        'group_slug' => 'display',
        'group_desc' => '',
        'attributes' => [
            [
                'attr_id'   => '456',
                'attr_name' => 'Screen size',
                'attr_slug' => 'screen_size',
                'attr_desc' => '',
                'value'     => '6.1"',
            ],
        ],
    ],
]
```

Four properties of that shape matter here.

Labels are copied into every product, so renaming a specification leaves every product
showing the old name until it is saved again.

Empty values are discarded at save time, so a missing entry already means "no value".
There is no stored empty in v1.

`true_false` is stored as the literal strings `'yes'` and `'no'`, and the frontend
template branches on those literals directly.

The frontend renders from the snapshot alone. `templates/shortcodes/specifications-table.php`
reads `attr_name` and `value` and never loads the term, so v1 renders values for
specifications that have since been deleted. The snapshot is the only surviving record
of those specifications.

ADR 0001 settled the set side: composition lives in one versioned post meta document
on the set.

## Decision

A product stores its values in one post meta key:

```txt
product_specifications_values
```

The value is a versioned document whose `values` member maps specification slug to
value:

```json
{
  "schema_version": 1,
  "values": {
    "screen-size-9f3a2b71": "6.1",
    "backlit-keyboard-2b71c4d0": true,
    "ports-c4d0e5f6": ["usb-c", "hdmi"]
  }
}
```

The assigned Specification Set is stored separately:

```txt
product_specifications_set    the Specification Set post_name
```

### Values are keyed by specification slug

The slug is the identity of a specification everywhere: in the value map, in the set
structure, and in import and export. There is no second key.

This works only because the slug cannot move. A specification slug is generated by the
plugin at creation and is never editable:

```txt
sanitize_title( name ) + '-' + 8 hex characters
screen-size-9f3a2b71
```

[ADR 0010](0010-specification-definition-and-identity.md) owns that rule, because it
belongs to the definition rather than to value storage. What this ADR depends on is only
that the slug is unique, frozen at creation, and unaffected by renaming the
specification.

### Term ids are not stored

The set structure carries slugs only. A term id is a runtime detail obtained by
resolving a slug, never a stored reference.

Two stored keys for one thing is a question nobody wants to answer when they disagree,
and the second key buys nothing measurable. `wp_terms` indexes both `term_id`
(clustered primary key) and `slug`, and the render path resolves a whole set in one
batched query either way:

```php
get_terms( [
    'taxonomy'               => SpecificationTaxonomy::KEY,
    'slug'                   => $slugs,
    'hide_empty'             => false,
    'update_term_meta_cache' => true,
] );
```

One term query and one term meta query for a set, whether it holds five specifications
or two hundred. `slug IN (…)` and `term_id IN (…)` are both a single index scan. The
per-item helpers — `get_term()` by id, `SpecificationDefinitionRepository::findByKey()`
by slug — are not to be called inside a render loop, and that is true regardless of
which key they take.

Dropping `term_id` amends the set item shape given in ADR 0001. `schema_version` stays
at 1: schema 1 has never shipped, so there is no stored document to migrate and no
consumer to break. This is a deliberate amendment in place, not an omission.

### A value is stored as its own type

The type's sanitizer decides what a stored value is: a string, an integer, a float, a
boolean, or an array for a composite type such as a number with a unit. Values are not
stringified on the way in. A type that needs structure gets structure without inventing
a second convention, and a numeric specification can be sorted and filtered without parsing.

Slug keys also remove a hazard that term id keys carry. `json_decode( $json, true )`
turns `{"456": "6.1"}` into `[456 => "6.1"]`, because PHP casts canonical decimal
strings to integer array keys. A key that changes type across a round trip is a bug
waiting for whoever writes `array_key_exists( '456', $values )`. A suffixed slug always
contains a hyphen and never casts.

### The document is versioned, and this is the document that needs it

ADR 0009 states the versioning policy for every stored document in the plugin:
structured data carries a `schema_version`, a bare scalar does not, the member is
declared as a plain integer with no `minimum` or `maximum`, the server stamps it on
write, and a stale document is upgraded by a dedicated upgrader service on read.

This is the document that policy exists for. A store carries one value map per product,
so a shape change can never be a wholesale rewrite — reading an old document and
upgrading it in place is the only affordable strategy, and that requires the schema to
accept a version it was not written against. `product_specifications_set` holds a single
`post_name` and is not versioned.

### An absent key is read against its context

Absence carries three different meanings, and each is resolved by something other than
the absence itself:

| Where | Absent key means | Resolved by |
| --- | --- | --- |
| On a product | No value was entered | The product is not a variation |
| On a variation | Inherit from the parent product | The product is a variation |
| For a specification whose value comes from elsewhere | Nothing is ever stored | The type draws no input, so nothing is submitted, and its `value()` computes the read |

The three never overlap. A variation is distinguishable from a product by its post
type, and a specification that stores nothing is distinguishable by its type drawing no
input, so no sentinel value is needed to tell them apart. ADR 0003 removes the derived
flag entirely: a type that reads from elsewhere draws no input and computes its value in
`value()`, so absence resolves against behavior rather than against a category.

Clearing a value removes its key rather than storing an empty string. One way to mean
nothing is enough, and storing empties would grow every product's meta with entries
that render as blank rows.

### A value the type cannot read is treated as absent

Changing a specification's type leaves values on every product that the new type was
not written for. Nothing rewrites them. The type coerces what it can on the way out and
treats the rest as absent:

```txt
number.read( '6.1"' )   →  6.1
number.read( 'large' )  →  absent
```

No stored data changes, no unbounded write is triggered by a UI action, and the same
rule covers a value written by a type whose plugin has since been deactivated. The
stored value survives, so restoring the original type restores the value.

## Rationale

The map is the single source of truth. Nothing else stores a value, and anything that
needs values arranged differently derives that arrangement and can rebuild it from the
map.

Labels are not copied. A specification's name, description, type and options live on
its term, so renaming one changes every product at once and no product ever holds a
stale label.

Keying by a frozen slug makes the whole model portable by construction. WXR carries
custom taxonomy terms with their slugs, and the WordPress Importer resolves an incoming
term with `term_exists( slug, taxonomy )`, reusing it when present and creating it when
not. Term ids change across a site move; slugs do not. A value map and a set structure
keyed by slug survive a native export and import intact, and so does the set assignment
now that it is stored as a `post_name` rather than a post id.

Keeping the assigned set in its own meta key keeps it queryable. A member of a
serialized array cannot be reached by `meta_query`, and "which products use this set"
is a question the migration asks and the admin will ask again. A `post_name` is as
queryable as an id.

## Consequences

### Positive

- Renaming a specification no longer leaves stale copies on products.
- A product's meta is a fraction of the v1 size: keys and values, no labels.
- One shape serves products and variations, so variation support needs no new storage
  concept.
- Values, set structures and set assignments survive a native WordPress export and
  import. Moving a site no longer requires a plugin-specific tool.
- Import and export (PS-057) reverts to being a merchant-facing packaging feature
  rather than a cross-environment id resolver.
- The migration has an unambiguous target.

### Negative

- Reading a product's table requires the set structure as well as the value map. The
  value map alone does not describe an order or a grouping.
- **Slugs are reusable and term ids are not.** Deleting a specification frees its slug,
  and a specification created later with the same name can take it and silently adopt
  orphaned values left on products. Deleting a specification must therefore purge its
  values from every product; PS-024 owns that, and it is not optional.
- A specification's key is frozen at creation. A merchant who dislikes a slug preserved
  from v1 cannot change it, because changing it means rewriting every product that
  holds a value under it. Renaming the label stays free.
- A value the current type cannot read is inert but still stored. It costs meta space
  until cleanup removes it.
- Concurrent writes to one product overwrite each other. The document is written whole,
  so a product edit, a REST call and a bulk job racing on the same product will lose
  one another's changes, last write winning. v1 behaves identically, so this is not a
  regression, and no ticket depends on it. PS-075 makes it routine rather than rare and
  is where a read-modify-write guard should be decided.

## Alternatives Considered

### Key the map by term id

Rejected. This was the original decision in this ADR and it was reversed.

The reasoning that supported it does not hold. It claimed portability was solved
because the set structure carries a slug beside each id, but that repairs the
*structure*, not the products. A value map of `{"456": "6.1"}` carries no slug, so after
a site move there is nothing to repair it from: the structure knows `screen_size` is now
term 891, and nothing anywhere knows that product 12's key `456` used to mean
`screen_size`. Term id keys make raw WordPress export and import lose every product
value, silently.

It also claimed a slug key would cost "a term query per row" at runtime. It would not.
The render path batches, and a batched query filtered on `slug` costs the same as one
filtered on `term_id`.

The one real advantage term ids retain is that they are never reused, which slugs are.
That is answered by making the value purge in PS-024 mandatory.

### Key the map by an immutable plugin-generated uuid on the term

Rejected. It is portable for the same reason a frozen slug is, and it is strictly worse
to work with: an opaque key that appears in exports and debugging output with nothing
legible in it, a uuid to backfill onto every term during migration, and a second
identity to keep in step with the slug the taxonomy already has. A frozen slug is a uuid
with a readable prefix and no extra column.

### Store the slug beside the value, `{"456": {"slug": …, "value": …}}`

Rejected. It repairs term id keys after a site move at the cost of roughly doubling
every product's meta and introducing a second copy of the slug that can disagree with
the term. Keying by the slug directly achieves the same repair with less stored data.

### Keep the v1 denormalized snapshot

Rejected. It is the cause of stale labels, it grows without bound, and every rename
requires touching every product.

### One meta key per specification, `_spec_screen_size`

Rejected. A product with forty specifications would carry forty meta rows, and reading
a table would be forty lookups or one query joined by a `LIKE` on the key.

### A custom database table

Rejected, consistent with ADR 0001. Core storage is sufficient, and a custom table
would need its own migration, its own backup story, and its own multisite handling.

### A bare map with no version envelope

Rejected. The structure document is versioned, and having one versioned document and
one unversioned one in the same plugin is a trap for whoever writes the next migration.

### Store an explicit empty rather than removing the key

Rejected for products. It creates two ways to mean nothing and grows meta with blank
rows. This has one open consequence, recorded below.

### Rewrite every product when a specification changes type

Rejected. It makes a UI action trigger an unbounded write, and it needs the background
processor to be safe. Coercing on read costs nothing and is reversible.

### Forbid changing a specification's type once it has values

Rejected. It is the only option with no stranded values at all, but it leaves a merchant
who picked the wrong type with no way forward.

## Consequences for the ADRs that follow

- **Derived values.** A specification whose value comes from elsewhere has no key in
  the map. ADR 0003 makes that a behavior rather than a flag, so PS-015 describes a
  pattern rather than a mechanism.
- **Variation overrides.** A variation stores a sparse document in this same shape, and
  an absent key inherits. The question this ADR deferred — how a variation overrides a
  parent value *to empty*, when removing the key is what inheritance means — is answered
  by ADR 0006: a stored `null`. Key absent inherits, a value overrides, `null` means the
  variation has no value. On a product, clearing still removes the key.
- **Defaults.** ADR 0007 keeps v1's model: one default, on the specification term, used
  as a prefill in the editor and stored when the product is saved, like any typed value.
  It is never resolved at read, and the set structure holds no defaults.
- **Save lifecycle.** ADR 0008: sanitize per type, write the whole document, fire the
  public actions. There is no type save action — a type subscribes to those actions like
  any third party. Anything else written is a projection and is rebuildable from the map.

## Migration target

The migration reads the v1 keys and writes the new ones:

| v1 | v2 |
| --- | --- |
| `_dwps_table` | `product_specifications_set`, resolved from post id to `post_name` |
| `_dwps_specification_table[].attributes[].attr_id` | resolved to the term's current slug, which becomes the key |
| `_dwps_specification_table[].attributes[].value` | that key's value |
| `group_*` and `attr_name`, `attr_slug`, `attr_desc` | dropped; they live on the term and in the set structure |

Five details the migration must not get wrong:

- **The key comes from `attr_id`, never from `attr_slug`.** The snapshot's `attr_slug`
  is a copy taken at save time, and v1 allows a slug to be edited afterward, so the two
  disagree on any product saved before a slug was changed. Resolve `attr_id` to the
  term and take its current slug.
- **A snapshot entry whose `attr_id` resolves to nothing is a deleted specification
  that v1 still renders.** The migration recreates it as a text specification from the
  snapshot's `attr_name`, `attr_slug` and `attr_desc`, and keys the value to it. This is
  the only moment the information exists: cleanup removes the v1 meta afterward. This is
  the sole legitimate use of the stale `attr_slug`.
- **`true_false` values are the strings `'yes'` and `'no'`.** They convert to booleans,
  and the renderer stops branching on the literals.
- **v1 already discarded empty values**, so an absent v1 entry migrates to an absent
  key, which means the same thing.
- **A preserved v1 slug can be a canonical integer string.** A specification named
  "2024" has the slug `2024`, which PHP would cast to an integer array key. The
  migration appends the suffix to any preserved slug that is numeric.

Slugs are preserved rather than regenerated. v1 exposes `dwspecs_attr_value_by( $postId, 'slug', … )`
as a public lookup, so rewriting existing slugs would break any theme calling it.

## Final Decision

```txt
product_specifications_values   versioned document, specification slug => value
product_specifications_set      the assigned Specification Set post_name
```

A specification slug is generated once, never editable, and is the only identity the
model stores. The map is the single source of truth. Labels live on the specification
term. Order and grouping live in the set structure. Anything else is a projection.
